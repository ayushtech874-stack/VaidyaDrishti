1. Core Concept & Legal Positioning ("Draft, Don't Decide")

The Clinical Problem

Doctors in small clinics and Tier-2/rural healthcare providers spend 50–70% of their consultation time on basic administrative intake (asking symptoms, duration, severity, past history, translating regional dialects). This reduces the time available for actual diagnosis and treatment.

Legal Guardrails in India

Under India's Telemedicine Practice Guidelines (TPG) 2020 and the Digital Personal Data Protection (DPDP) Act 2023:

  • AI is NOT legally permitted to independently diagnose patients, prescribe medicines, or provide clinical opinions.
  • AI must remain strictly a decision-support and documentation tool under a Registered Medical Practitioner's (RMP) full responsibility.
Design Principle: "Draft, Don't Decide"
VaidyaDrishti organizes unstructured patient voice/text into a clean 5-field clinical draft and highlights emergency protocol red flags. The doctor retains 100% clinical authority and makes all medical decisions.

3. How is Urgency Checked?

Urgency is checked using a 100% deterministic TypeScript rules engine located in your codebase at lib/rules-engine/index.ts.

It checks patient symptoms against medical guidelines from the Manchester Triage System (MTS) and WHO IMAI protocols. It uses a 2-tier input evaluation:

  1. Matches structured symptoms extracted by Groq Llama 3.3.
  2. Runs a keyword safety net across the raw transcript (matching English and Romanized regional terms like "chhati me dard" or "saans phool").

4. How You (As Admin) Add or Edit Red-Flag Rules

All red-flag rules are stored in plain, readable TypeScript in:
d:\VaidyaDrishti\lib\rules-engine\index.ts

To add a new red flag rule (for example, adding a rule for Severe Bleeding or Dengue / High Fever with Rash), simply open lib/rules-engine/index.ts and add a condition like this:

// Example: Adding a NEW High Urgency Rule for Severe Bleeding
if (matchPattern(allSymptomsText, [/severe\s*bleeding/i, /khun\s*nikal/i, /heavy\s*bleeding/i])) {
  redFlags.push('HIGH: Severe or uncontrolled bleeding reported (WHO IMAI Emergency Flag)');
}

// Example: Adding a NEW Medium Urgency Rule for High Fever + Joint Pain (Dengue/Chikungunya)
if (hasFever && matchPattern(allSymptomsText, [/joint\s*pain/i, /joron\s*me\s*dard/i])) {
  redFlags.push('MEDIUM: Fever accompanied by severe joint pain (Suspected Dengue/Chikungunya)');
}
💡 Pro-Tip for Admins: Because red-flag rules are written in standard TypeScript code inside lib/rules-engine/index.ts, any rule you add or edit takes effect instantly across all channels (WhatsApp + Web Form) without requiring any database changes!

10. Multi-Doctor Isolation, Private Clinic Onboarding & Single DB Architecture

1. Do You Need a New Database for Every Doctor/Clinic?

NO! You do NOT need to build a new database for every doctor or clinic.

VaidyaDrishti is designed as a Single Database Multi-Tenant Architecture using Supabase Postgres Row Level Security (RLS):

  • One Central Database: Houses all patient intakes across all participating clinics.
  • Clinic Isolation via clinic_id / assigned_doctor_id: Every intake row has a column tagging which doctor or clinic it belongs to.
  • Cryptographic Isolation (RLS): When Dr. Ramesh logs in, the database automatically filters and returns only Dr. Ramesh's patients. Dr. Anita cannot see Dr. Ramesh's patients, even though they share the same database.
[CENTRAL SUPABASE DATABASE]
 ├── Clinic A (Dr. Ramesh)  ──► Sees ONLY Patients A1, A2, A3
 ├── Clinic B (Dr. Anita)   ──► Sees ONLY Patients B1, B2, B3
 └── Clinic C (Dr. Patel)   ──► Sees ONLY Patients C1, C2, C3

13. Critical Pre-Scale Gaps, Multilingual Safety Caveats & Production Audits

⚠️ Crucial Pre-Scale Audit Notice: Before expanding from a 1-clinic pilot to multi-clinic production, these 8 operational and architectural realities must be addressed.

1. Multi-Clinic Schema Isolation (`clinic_id`) is Priority #1

Current pilot code assumes 1 clinic. Moving to multi-clinic requires adding a strict clinic_id UUID column across patients, intakes, doctors, and audit_logs with RLS policies restricting doctors to their auth.jwt() -> clinic_id claim. This must be executed before onboarding Clinic #2 to prevent data leakage migration pain.

2. Multilingual Safety Caveat (Whisper ASR vs Keyword Safety Net)

While Groq Whisper transcribes 90+ languages (Kannada, Marathi, Telugu, Tamil, Bengali, Punjabi), the deterministic fallback keyword safety net inside lib/rules-engine/index.ts currently has verified regex patterns only for English and Hindi/Hinglish (e.g. "chhati me dard", "saans phool"). Non-Hindi languages rely on LLM structuring alone.
Compliance Requirement: Expand multi-lingual regex dictionaries (e.g., Kannada "thale novu", Tamil "marbu vali") into the rules engine before claiming equal deterministic protection across all 8 regional languages.

3. Dedicated Super-Admin Control Panel

Managing doctors, updating clinic WhatsApp accounts, or tweaking triage rules by hand-editing code or Supabase SQL will not scale. A secure /admin panel is required for onboarding new clinics, managing RMP credentials, and viewing network-wide uptime metrics.

4. Automated System Health & Outage Monitoring

Relying on manual daily checks by doctors breaks at scale. Production rollout requires automated error tracking (e.g., Sentry) and background ping monitors to alert admins instantly if Groq API rate limits occur or Twilio webhooks fail.

5. Cost Modeling & API Rate Limits (429 Traffic Ceilings)

Resource Pilot Volume (1 Clinic) Production Scale (10 Clinics) Risk / Mitigation
Groq LLM / Whisper Free Tier (~50 calls/day) Paid Tier (~1,000+ calls/day) May hit free tier rate limits (429 error). Must upgrade to Groq Developer Paid Tier and implement exponential backoff retry logic.
Twilio WhatsApp Free Sandbox ~₹0.40 per chat session Budget ~₹400 per 1,000 patient intakes. Require utility conversation token management.

6. ASHA Worker Offline PWA Consent Architecture

Capturing village intakes offline via a Progressive Web App (PWA) introduces a DPDP Act consent challenge.
Design Solution: The PWA must record a cryptographic, time-stamped digital consent signature locally on-device and defer AI processing on the server until the consent record successfully syncs upon regaining network connectivity.

7. ABDM / ABHA Integration Sandbox Certification Reality

Connecting to India's National Health Authority (NHA) ABDM stack is not just an API endpoint. It requires a multi-month empanelment process, including sandbox functional testing, security vulnerability audits (VAPT), and official M1/M2/M3 ABDM milestone certification.

8. Backup & Disaster Recovery (DR) Protocol

Supabase provides daily automated Postgres backups and Point-In-Time-Recovery (PITR) on Pro tiers. Before going live with real multi-clinic PII, verify that 7-day PITR is active and run a quarterly restore drill to a staging database.

15.4 Multi-Hospital Super-Admin Hierarchy & Tenant Data Isolation

When multiple independent hospitals or private clinics adopt VaidyaDrishti, the system enforces a strict 2-Tier Administrative Hierarchy:

  • Tier 2: Hospital Lead Doctor / Chief Medical Officer (CMO): Manages their clinic's clinical queue. Under Postgres Row Level Security (RLS), Hospital A's doctors can never see Hospital B's patient data, guaranteeing 100% tenant isolation between competing health providers.
  • How Admins Identify Doctor Queues: The Super-Admin Page features the Empaneled RMP Doctors Directory Table listing every doctor's Name, Email, RMP License Number, and assigned clinic_id. 15.5 Account Provisioning Architecture: Sign-In vs. Sign-Up

  • Patient Intake (Frictionless / Passwordless): Patients do not create password accounts. They submit symptoms via the Web Form (/patient/intake) or WhatsApp Bot using their Name, Age, Phone, and DPDP digital consent. This eliminates onboarding friction in rural village settings.
  • Doctor & Admin Sign-In (/doctor/login): Doctors and Admins log in through a single unified portal. Upon authentication, Next.js inspects app_metadata.role:
    • If role === 'super_admin' → Automatically routes to /admin.
    • If role === 'doctor' → Automatically routes to /doctor/dashboard.
  • Doctor Sign-Up / Empanelement Protocol: Under Telemedicine Practice Guidelines (2020), open public signup for doctors is prohibited to prevent fake doctor accounts. Instead, doctor accounts are empaneled by the Super-Admin via the Supabase Admin API (set-super-admin.ts) with their official RMP license registration number attached.

16. Multi-Hospital & Multi-Department Scaling Architecture & Super-Admin Operations

🏥 Enterprise Multi-Hospital Blueprint: To scale VaidyaDrishti across large hospital chains and multi-specialty healthcare networks, the architecture extends from a single-clinic model to a 3-Tier Enterprise Hierarchy: Platform Super-Admin → Hospital Network → Medical Departments → Empaneled RMP Doctors.

16.1 Database Schema Design for 3-Tier Enterprise Hierarchy

To connect 2 or more hospitals with multiple departments (Cardiology, Orthopedics, Pediatrics, General Medicine, Gynecology) and multiple doctors under each department, the Supabase Postgres relational database schema is structured as follows:

-- 1. HOSPITALS / CLINIC NETWORKS TABLE
CREATE TABLE hospitals (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,                  -- e.g. "Apex City Hospital"
  code TEXT UNIQUE NOT NULL,           -- e.g. "HOSP_APEX"
  location TEXT,                       -- e.g. "Bengaluru, KA"
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 2. MEDICAL DEPARTMENTS TABLE
CREATE TABLE departments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  hospital_id UUID REFERENCES hospitals(id) ON DELETE CASCADE,
  name TEXT NOT NULL,                  -- e.g. "Cardiology", "Pediatrics"
  code TEXT NOT NULL,                  -- e.g. "DEPT_CARDIO"
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(hospital_id, code)
);

-- 3. EMPANELED DOCTORS TABLE (Linked to Hospital & Department)
CREATE TABLE doctors (
  id UUID PRIMARY KEY REFERENCES auth.users(id),
  hospital_id UUID REFERENCES hospitals(id),
  department_id UUID REFERENCES departments(id),
  name TEXT NOT NULL,
  email TEXT UNIQUE NOT NULL,
  rmp_registration_number TEXT NOT NULL,
  role TEXT DEFAULT 'doctor',          -- 'super_admin', 'hospital_admin', 'dept_head', 'doctor'
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 4. PATIENT INTAKES TABLE (Multi-Tenant Tagged)
CREATE TABLE intakes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  hospital_id UUID REFERENCES hospitals(id),
  department_id UUID REFERENCES departments(id),
  patient_id UUID REFERENCES patients(id),
  raw_text TEXT NOT NULL,
  structured_data JSONB,
  urgency_level TEXT,                  -- 'high', 'medium', 'low'
  status TEXT DEFAULT 'pending_review',-- 'pending_review', 'doctor_reviewed'
  created_at TIMESTAMPTZ DEFAULT NOW()
);

16.2 4-Tier Permission Hierarchy & Row Level Security (RLS)

Role Level JWT app_metadata Claim Access Boundary & Permissions
Level 1: Platform Super-Admin { role: "super_admin" } Full read/write/edit control across all hospitals, departments, doctors, and audit logs. Managed via /admin.
Level 2: Hospital Admin (CMO) { role: "hospital_admin", hospital_id: "HOSP_A" } Can view all departments, doctors, and patient intakes within Hospital A. Cannot view Hospital B.
Level 3: Department Head { role: "dept_head", hospital_id: "HOSP_A", department_id: "DEPT_CARDIO" } Can view all Cardiology patient intakes and doctors within Hospital A.
Level 4: Attending RMP Doctor { role: "doctor", hospital_id: "HOSP_A", department_id: "DEPT_CARDIO" } Can view and review active patient intakes in their assigned department queue.
